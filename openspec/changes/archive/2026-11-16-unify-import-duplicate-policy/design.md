# Design

## Context

见 `proposal.md - Why`。当前相关实现：

- `js/import.js`：`parseText` 同时承担解析与校验。文件内重名会写入 `errors`，导致 `ok:false`、`categories:[]`；重复分类行虽已把歌名并入第一个同名分类（`current = first.category`），但仍被记成错误。`planReplace` 固定返回 `skipped: []`，`planAppend` 才产出项目级跳过项。
- `js/app-import-export.js`：解析失败进入只读错误弹窗；成功后 `confirmImport` 生成计划并渲染预览。替换预览只描述分类增删与歌名更新，追加预览才显示跳过项。
- `js/playlist-check.js`：编辑器与追加计划共用的查重键（`trim` 后区分大小写）、索引与重复分组。项目 schema 与编辑器仍强制全局唯一。
- 导入是“解析 → 计划 → 确认 → 提交”的纯逻辑链路，`applyImport` 不感知重复。

## Goals / Non-Goals

**Goals:**
- 文件内重复从“解析错误”变成“解析结果的一部分”，由同一条跳过/合并规则覆盖替换与追加。
- 确认预览与完成摘要能完整解释“哪些行没进来、为什么”。
- 保持唯一性约束与原子性，不引入自动改名或序号。

**Non-Goals:**
- 不放开编辑器、项目文件 schema、导出往返的唯一性校验。
- 不把重复变成交互式逐项决策（不提供“保留重名/自动加后缀”）。
- 不改变编码识别、分类/歌名解析、版面保留与歌名顺序规则。

## Decisions

1. **去重在解析阶段完成，计划阶段只做项目级去重。**
   `parseText` 对重复歌名保留首行、跳过后续行，对重复分类名沿用已有合并语义，并把结果作为结构化元数据输出。理由：文件内重复是“文件本身的事实”，替换与追加都必须消费同一份去重结果；放在计划阶段会让替换路径也要重新扫描一遍。
   备选：只在 `planAppend` 去重、替换模式继续报错——放弃，正是当前不一致的来源。

2. **解析结果携带文件级元数据，`planImport` 接受两种输入形态。**
   解析返回 `{ categories, skipped, mergedCategories }`，其中 `skipped` 每项为 `{ song, line, firstLine }`，`mergedCategories` 为 `[{ name, lines }]`。`planImport(project, parsedOrCategories, mode)` 在收到数组时按“无文件级重复”处理（保持现有测试与调用方式可用），收到对象时把文件级跳过项归一化并合并进计划的 `skipped`。
   理由：单一报告出口，`planReplace`/`planAppend`/预览/摘要都读 `plan.skipped`，不必让 UI 同时拼两处数据。

3. **跳过项统一为带来源的记录。**
   `plan.skipped` 每项形如 `{ song, source: 'file' | 'project', line?, firstLine?, category? }`：`file` 带原始行号与首次出现行号，`project` 带当前所在分类。追加模式同时存在两类时按各自来源并列展示，不做合并；同一歌名既在文件内重复又与项目冲突时两条都保留，因为它们解释的是不同原因。

4. **分类合并通过 `mergedCategories` 提示，而不是写进 `skipped`。**
   “同名分类已合并”不是“某行没导入”，混入跳过列表会误导统计；预览单独一段提示，并给出被合并的分类名与行号。

5. **替换与追加共用同一套预览结构。**
   预览分四块：新增/删除分类、歌名更新或并入统计、同名分类合并提示、跳过项列表。替换模式此前缺少后两块，本次补齐；追加模式删掉“仅追加才显示”的分支判断。零新增的禁用条件改为“追加模式且 `stats.addedSongs === 0`”，保持不变。

6. **统计口径统一。**
   `stats.skippedSongs` 包含文件级与项目级跳过总数；完成 toast 报出导入数量与跳过总数。`applyImport` 不修改，因为 `plan.categories` 已经是去重后的结果。

7. **不新增共享模块。**
   文件内首次出现索引就地复用 `L.playlistCheck.key`/`index` 的语义即可；不为了两处相似逻辑再抽一层。若实现时发现 `parseText` 的索引与 `playlistCheck.index` 完全重合，可改为直接调用后者，但不新增文件。

## Risks / Trade-offs

- [替换模式更“宽容”，用户可能没注意少数行被丢弃] → 跳过列表常驻预览且带行号；主按钮文案保持“继续导入”，确认框已是一次显式确认。仍接受：这是“导入成功但少几行”与“整单失败”之间的取舍。
- [现有测试与示例文件按“重复即失败”编写] → 同步更新 `samples/duplicate.txt` 的用途说明与 `import.test.js` 断言；`playlist-check.test.js` 只测索引/分组，不受影响。
- [同名分类合并可能被理解为两个分类块] → 预览明确提示合并及行号；需求本就禁止重名分类，合并是唯一合法解释。
- [跳过项很多时列表过长] → 预览滚动区域现有样式可承载；是否折叠留到实现时按截图判断，不影响行为契约。
- [大小写不同仍算不同歌名] → 本次不改判定规则，保持与追加去重、编辑器一致。

## Migration Plan

无数据迁移：不改草稿结构、项目文件 schema 或导出格式。发布时同步更新 `README.md` 与 `docs/歌单生成器需求.md` 的表述；回滚即回退本次提交，旧文件会恢复“重复即失败”的旧行为。
