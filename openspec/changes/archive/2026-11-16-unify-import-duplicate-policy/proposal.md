# Proposal

## Why

导入目前对“重复”有两套互不一致的处理：文件内部出现重名会直接判整份文件失败（用户只能改文件重来），而与项目现有歌名重复却只是跳过并在确认框列出。同一个概念、两个结果，用户无法预期，一行手滑就能让几百首的导入全部作废。

## What Changes

- 文件内部重复歌名不再视为导入错误：保留第一次出现，后续同名的行被跳过，并连同行号列在确认信息里。判定规则与追加去重一致：去除首尾空白后逐字符相等（区分大小写），范围为整份文件。
- 文件内部重复分类名不再视为导入错误：沿用解析器已有的合并语义，把后续同名分类下的歌名并入第一次出现的分类，并在确认信息中提示“同名分类已合并”。合并后如出现重复歌名，同样按上一条跳过。
- “替换全部”的确认预览补上被跳过的行：文件内重复、以及因同名分类合并产生的重复，都要逐条可见，避免替换掉现有歌单时静默丢数据。
- “追加到现有歌单”保持现有行为（跳过项目内已存在的歌名、逐条列出原分类），并与文件内去重共用一套口径；两类跳过在预览中分别标注来源。
- 仍然保留歌名/分类名唯一性约束：编辑器校验、项目文件 schema、导出往返均不放开。导入只负责丢弃重复行，不自动改名、不追加序号。
- 仍然保持原子性：空分类名、空文件、无法解码等真正的解析错误继续拒绝整次导入；被跳过的重复行不产生任何部分写入，也不单独产生撤销记录。

**BREAKING**：曾经因“文件内重名”而失败的导入现在会成功（内容为去重后的子集）。

### Modified Capabilities

- `playlist-import`: 「重名校验」从“文件内重复即整体失败”改为“文件内重复跳过并报告、同名分类合并”；「导入原子性」的触发条件收窄到真正的解析错误；导入确认信息需要覆盖替换与追加两种模式下的全部跳过项。

## Impact

- `js/import.js`：`parseText` 的重名策略（错误 → 跳过/合并 + 结构化 `skipped`）；`planReplace`/`planAppend` 的跳过项结构与统计口径；`applyImport` 不变。
- `js/app-import-export.js`：替换预览新增跳过列表；追加预览区分“文件内重复”与“项目已存在”；toast/禁用条件沿用更新后的统计。
- `js/playlist-check.js`：可能新增统一的“文件内首次出现”索引辅助，避免导入与编辑器各写一份。
- 测试：`scripts/checks/import.test.js` 与 `scripts/checks/playlist-check.test.js` 需覆盖新的跳过语义；`samples/duplicate.txt` 从“失败样例”变为“去重成功样例”。
- 文档：`README.md` 歌单格式说明与 `docs/歌单生成器需求.md` 的“分类和歌名不允许重名（报错提醒）”表述需要同步为“文件内重复跳过并提示”。
