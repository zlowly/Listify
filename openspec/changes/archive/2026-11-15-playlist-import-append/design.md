# Design

## Context

现有导入是单入口、强校验、整份替换：`handleImportFile` 解码并 `parseText`，文件内部重名直接判失败；成功后用 `reconcile` 预览分类增删，再由 `applyImport` 替换 `project.playlist.categories`，并删除画布上已不存在的分类块。歌单编辑器另有一套独立的重复扫描：`validate()` 用 `songPositions` 标红，但提示只有“与另一首歌重复”，不指出冲突位置。

本次改动要在不改变入口、解析、编码识别和替换语义的前提下加入追加，并让导入与编辑器共用同一套查重和提示。约束来自 `AGENTS.md` 与 `code-architecture`：零构建、经典脚本、单向依赖、纯逻辑可在 Node 中测试、新增职责单独成文件。需求见 `proposal.md` 与 `specs/`，此处只说明实现方式。

## Goals / Non-Goals

**Goals:**

- 在现有确认弹窗内选择“替换全部 / 追加到现有歌单”，默认替换；项目为空时保持直接导入。
- 追加不删除任何分类、分类块或歌名，按分类名并集去重，新歌名按文件顺序接在末尾。
- 追加时保持“歌名全项目唯一”，重复项跳过并报告当前位置，不自动改名。
- 歌名查重、冲突定位和提示文案只有一处实现，导入与歌单编辑器结果一致。
- 逻辑层可被 `node --test` 覆盖，不引入依赖或构建步骤。

**Non-Goals:**

- 不做逐条冲突解决、自动加后缀、按歌手/版本合并或跨项目合并。
- 不改变文件格式、编码识别、文件内重名拒绝策略和替换导入的版面保留规则。
- 不重做歌单编辑器布局；只改校验、提示与页脚摘要。
- 不新增多步撤销；追加仍是一次可撤销操作。
- 不改变草稿数据结构或 IndexedDB schema。

## Decisions

### 1. 方式选择放在现有确认弹窗内，解析之后

解析成功后，如果项目已有分类，弹窗同时承担“预览 + 选方式”；默认选中“替换全部”。项目没有分类时没有可追加的对象，直接按替换应用，不弹选择。切换单选项时用当前文件分类重新计算计划并重绘预览，不重新读文件、不重新解码。

理由：保持单入口和现有“先解析、后确认”的节奏；用户在看到增删预览的同时决定方式，避免两个按钮或二次弹窗。备选方案“工具栏放两个导入按钮”会复制入口并改变肌肉记忆；“先替换再提示撤销”把风险留到事后；“默认追加”破坏现有用户预期。

### 2. 解析与文件内校验完全复用，追加只改变合并阶段

`parseText` 的“文件内分类名唯一、歌名唯一、空分类名、无内容”仍是一次导入的准入门槛，两种模式一致。文件内重复仍整份拒绝，不做自动去重。

理由：文件是作者的输入单元，文件内部自相矛盾时静默取舍会丢内容；保持现有错误提示和原子性。备选“追加时容忍文件内重复”会让同一文件在两种模式下行为不同，难以解释。

### 3. 用纯函数生成计划，应用阶段只执行计划

新增 `L.importer.planImport(project, categories, mode)`，不修改入参，返回统一计划：

```
{
  mode: 'replace' | 'append',
  categories: [...],                  // 应用后的完整分类副本
  addedCategoryNames: [...],          // 新分类（追加时未放置）
  mergedCategories: [{name, addedSongs, skippedSongs}],
  unchangedCategoryNames: [...],      // 追加模式下没有新增的分类
  removedCategoryNames: [...],        // 仅替换模式
  skipped: [{song, category}],        // 仅追加模式，已存在歌名及其所在分类
  stats: {newCategories, addedSongs, skippedSongs, songUpdates}
}
```

替换模式的计划复用现有 `reconcile` 与 `countSongChanges`，行为不变；追加模式先由 `L.playlistCheck.index(project.playlist.categories)` 建立 `trim(歌名) → {category, categoryIndex, songIndex}` 索引，再按文件分类顺序和文件歌名顺序遍历：能命中的记入 `skipped`，未命中的追加到同名分类（不存在则新建空分类）并立即写回索引，保证同一文件内后出现的同名歌也被跳过。

`applyImport(project, plan)` 统一执行：写入 `plan.categories` 的副本；仅当 `plan.mode === 'replace'` 时删除画布上名称不在新集合内的分类块。追加模式永不删除元素，也不改动已有歌名的相对顺序。

理由：计划是纯数据，弹窗预览、追加计算和测试都围绕它；UI 不需要理解合并规则。备选“在 `handleImportFile` 里直接改项目再确认”无法取消，也难测；“在 UI 层分支合并”会把领域规则散到事件处理里。

### 4. 全项目查重，重复只跳过并报告

`L.playlistCheck` 的键是 `song.trim()`，逐字符相等且区分大小写；不做全半角、大小写或标点归一化。追加时只要项目任何分类已有该键就跳过，记录它当前所在分类。系统不自动改名、不移动、不调序；提示用户自行加歌手等信息。

理由：这是用户明确保留的全局唯一不变式，编辑器、排版和导出都依赖它；跳过而非拒绝整份文件，才能让追加在部分重叠时仍然可用。备选“只在目标分类内查重”会让编辑器随后报错；备选“自动加 (2)”会制造用户不认识的歌名；备选“整份拒绝”会让用户为几首重复歌反复改文件。

### 5. 新分类即使 0 首新增也创建

追加时，文件声明的新分类先创建为未放置分类，再逐首并入；若所有歌名都已存在，分类仍保留并在摘要中标注“0 首新增”。`未分类` 按同名分类处理，并入现有 `未分类`。

理由：分类是文件表达的结构信息，静默丢掉会让用户以为导入失败；保留后用户可自行删除。备选“0 首不创建”会隐藏文件内容，也让“为什么这个分类没出现”难以解释。

### 6. 共享模块 `js/playlist-check.js`

模块挂在 `L.playlistCheck`，纯逻辑、无 DOM/canvas/存储依赖，放在 `index.html` 的 `js/model.js` 之后、`js/layout.js` 与 `js/import.js` 之前。对外职责：

- `key(song)`：`trim` 后的查重键。
- `index(categories)`：一次遍历建立键到分类/分类序号/歌名序号的映射。
- `analyze(categories)`：返回重复分组 `{song, occurrences:[{category, categoryIndex, songIndex}]}`、单元格到分组的索引、分组数与冲突单元格数；只在需要时生成文案。
- `cellMessage(group, occurrenceIndex)`：指向同组中另一个单元格，例如 `与「摇滚」第 2 首同名`。
- `groupMessage(group)` / `summary(groups)`：汇总文案，例如 `2 首歌名重复：晴天（流行 / 摇滚）、后来（摇滚 / 未分类）`。
- `HINT`：`相同歌名不会被自动修改。如要同时保留，请在歌名后加上歌手等信息（如「晴天 - 周杰伦」）。`

导入追加计划只用 `index()`；编辑器用 `analyze()` 同时得到标红位置和页脚摘要。文案常量放在该模块，保证两处一致。

理由：`import.js` 是导入领域模块，让编辑器依赖它会造成方向倒置；`ui-playlist-editor.js` 在 Node 测试里被 loader 跳过，不能承载可测逻辑；`model.js` 已接近体量上限且职责不同。备选“各写一份扫描”会在提示位置和边界条件上漂移，正是本次要消除的问题。

### 7. 编辑器：一次分析，单元格具体提示，页脚常驻摘要

`validate()` 先做空值、`#` 开头和分类名检查，再用一次 `analyze(categories)` 标记重复；重复格的提示改为 `cellMessage`，不再使用笼统文案。`updateValidation()` 复用这次分析结果，避免按分类反复扫描；页脚在存在重复时展示 `summary(groups)` 与 `HINT`，让用户即使不在冲突分类也能看到全局重复。`applyButton.disabled` 规则不变；“应用”处理器仍会重新校验一次作为兜底。

单元格指向规则：每个重复项指向同组中第一个不同单元格的 occurrence（两项时互指；多项时指向下一项），避免提示自己。单元格文案按当前分类懒生成，页脚摘要按分组生成。

理由：现有规格要求“提示与哪首歌重复”且“应用不可用”，Option A 在不改变交互的前提下补足信息；页脚解决“重复发生在别的分类、当前格只看到一句话”的定位问题。备选“弹窗列出全部错误”打断编辑流；“只改单元格”在跨分类冲突时仍难定位。

### 8. 预览与零新增

追加预览按分类分组展示：新增分类（未放置）、并入分类（+N 首 / 跳过 M 首）、无变化分类、跳过歌名及其当前分类，并附 `HINT`。若追加计划的新增歌名为 0，确认按钮禁用并显示“没有新增内容”，不产生撤销记录。

理由：追加可能是空操作；提前说明比事后 toast 更清楚。列表较长时由弹窗内容区滚动，不截断冲突信息。替换预览继续显示新增分类、将删除分类块和歌名更新数。

### 9. 性能取舍

在当前实现上实测（Node 2026-11-15）：`index()` 处理 1000 首约 0.03–0.04 ms，3000 首约 0.12 ms，10000 首约 0.48 ms；`analyze()` 1000 首约 0.05 ms，10000 首约 0.68 ms；1000 首全部成对重复时 `analyze()` 约 0.044 ms，连同生成 1000 条单元格文案约 0.08 ms。相对 16.7 ms 帧预算可忽略，因此不做防抖，也不为查重引入缓存。

真正的主成本是现有 DOM 同步：`updateValidation()` 会遍历当前分类所有单元格，分类名输入会重建左侧列表，`categoryHasError()` 目前按“分类 × 错误”扫描。本次只把重复扫描降为一次，并让分类错误判断复用分析结果；不改变 DOM 更新频率。若日后大歌单输入出现卡顿，再单独优化“只更新当前格 + 每分类错误计数”，不在本次扩大范围。

### 10. 文案与统计口径

- 追加成功：`已追加 N 个分类，新增 M 首歌名，跳过 K 首重复（编码）。`
- 替换成功：保持 `已导入 N 个分类、M 首歌名（编码）。`
- 零新增：`没有新增内容：M 首歌名均已存在。`
- 跳过行：`「晴天」已存在于「流行」（不重复添加）`
- 编辑器单元格：`与「流行」第 1 首同名`
- 编辑器摘要：`2 首歌名重复：晴天（流行 / 摇滚）、后来（摇滚 / 未分类）`

统计以“计划”为准：新增分类数、实际写入歌名数、跳过数；替换模式的歌名更新数沿用 `countSongChanges` 的多重集口径，避免把纯换序算成修改。

## Risks / Trade-offs

- [用户忽略跳过的歌名] → 预览给出数量、歌名和当前分类，页脚/提示重复出现；零新增时明确阻止继续。
- [已有歌单时每次导入都多一步选择] → 默认替换且动作仍是“继续导入”，只多一次确认；换来实现追加能力的最小交互成本。
- [追加的分类改名被理解为“改名”] → 预览把旧分类列为“无变化”、新名称列为“新增分类（未放置）”；规格已明确不继承旧块样式。
- [共享模块成为新的全局依赖] → 在 `index.html` 固定顺序声明，loader 自动加载，并用 Node 用例覆盖其纯逻辑。
- [重复很多时页脚摘要过长] → 页脚只做一行摘要并允许换行/滚动，逐格提示承载细节；不截断冲突分组。
- [全半角或大小写差异被视为不同歌名] → 与现有编辑器、排版口径一致；规格明确“trim 后逐字符相等、区分大小写”，避免两套归一化规则。
- [计划在预览后过期] → 计划只用于一次确认；应用前不重新读取项目，若用户在弹窗期间通过其他入口改项目，关闭后重新导入即可，现有单线程交互下不会并发写。

## Migration Plan

1. 新增 `js/playlist-check.js` 与 `index.html` 脚本声明，先以 Node 用例固定 `index`/`analyze`/文案行为。
2. 改造 `js/import.js`：加入 `planImport`，让 `applyImport` 接受计划并按模式决定是否删除分类块；保留 `reconcile` 供替换分支使用。
3. 改造 `js/app-import-export.js`：确认弹窗加入方式选择与两种预览，空项目直接应用，追加零新增短路。
4. 改造 `js/ui-playlist-editor.js`：用共享分析替换本地重复扫描，补单元格定位提示与页脚摘要。
5. 运行 `node --test scripts/checks/*.test.js`，再用浏览器手动/`agent-browser` 走导入、追加、编辑器三条路径。
6. 发布时照常执行 `./build.sh`；无数据迁移、无 feature flag，回滚即还原文件，草稿格式不变。

## Open Questions

无。分组折叠、摘要换行等展示细节可在任务内按现有弹窗样式决定，不改变规格、方案或任务拆分。
