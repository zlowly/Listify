# Design

## Context

画布排版每次都会对分类歌名做一次稳定排序（`js/layout.js` 的 `layoutCategory` 调用 `sortSongs`），所以项目里保存的歌名顺序从不出现在画布上；歌单编辑器的网格却按保存顺序展示。两个顺序各自成立，谁也没有错，缺的是一个把「画布已经在用的顺序」写回数据的显式动作。

编辑器已经具备所需的提交机制：打开时复制出工作副本（含 `originalName` / `originalSongs` 用于取消与还原），「应用」时整体提交并压入一步撤销。校验是逐字重算的，错误以位置为键（`song:<分类>:<序号>`）。排序会改变位置，因此必须重新走一遍完整校验，而不是补丁式改 class。

## Goals / Non-Goals

**Goals:**

- 提供一个显式动作，让当前分类的保存顺序与画布顺序一致。
- 排序结果可预览、可取消，提交后只占一步撤销。
- 应用摘要能区分「重排」与「改名」，不再把重排误报成歌名改动。
- 排序口径与排版共用一个实现，结构上不允许两处规则漂移。

**Non-Goals:**

- 不改变画布的排序规则，也不让它可配置。
- 不提供降序，不在导入或应用时自动排序。
- 不改变导入解析、项目文件格式或分类块的任何排版参数。
- 不重构编辑器的校验与提交架构（只在其上接入排序）。

## Decisions

### 在工作副本里物理重排，而不是只改网格的展示顺序

备选方案：网格按排序结果展示但保存原顺序；应用时自动排序；给分类加一个「已排序」标记。

- 纯展示排序会让「保存顺序」和「看到顺序」继续分叉，用户改完一个格子后位置会跳回去，而且这个动作没有任何可提交的效果。
- 应用时自动排序会在用户不知情时重写数据，与「取消可丢弃」冲突。
- 标记位引入新的持久化状态，最终仍要在某处生成排序后的数组。

选择物理重排：只有数据本身变了，取消/撤销/摘要这些已有机制才有明确对象；用户也能在应用前看到结果。

### 复用排版自己的排序函数

排序键（虚拟字数、同宽稳定）只在排版侧定义一次。按钮调用同一个函数，因此「按钮排出来的顺序」和「画布排出来的顺序」不可能因为两份比较器而分叉；以后若调整排序口径，按钮自动跟随。代价是编辑器要依赖排版模块的导出，这一点它本来就在同一个全局命名空间内。

### 幂等靠比较顺序，而不是比较对象引用

触发时先取出「当前顺序」与「排序后顺序」的文本序列做逐项比较；相同则只给提示，不改数据、不重渲染、不制造脏状态。这样重复点击不会让「应用」按钮误以为有改动，也不会让撤销栈出现空步骤。

### 排序后重跑整表校验

位置的键会失效，所以排序后走已有的重渲染与校验刷新路径（重建网格 → 重新计算错误集合 → 重新标记与计数），而不是就地把错误从一个格子搬到另一个格子。跨分类的重复歌名本来与位置无关，重算后自然保持标红；错误位置也会跟着歌名走，不会出现「红框留在空位上」。

### 摘要用多重集比较，排序单列

`countSongChanges` 目前按索引对比，重排会把几乎每首都算成改动。改为按去掉首尾空白后的歌名做计数比较：同名的数量差才是真实的增删改，重排不产生差异。摘要里另起一句报告「N 个分类已排序」，让用户知道这次提交的有效内容是什么。备选是保留索引比较、在排序时特判——那需要把「哪些改动来自排序」一路传下去，且用户既排序又改名时仍会误报。

### 排序后焦点落在触发按钮上

重渲染会销毁网格里的输入元素。与其尝试追踪某个歌名的新位置（同名歌名、同字数歌名的落点并不唯一），不如把焦点放回排序按钮；结果通过状态行或提示播报。键盘用户按下按钮后不会丢失位置。

## Risks / Trade-offs

- **排序后画布毫无变化，用户以为按钮没生效** → 按钮文案与提示明确「与画布顺序一致」；排序后状态行报告本次移动了多少首，而不是只说「完成」。
- **排序结果被随后的重新导入覆盖** → 这是规格里明确的行为（导入用文件顺序覆盖），在导入确认文案与规格场景中保持一致即可。
- **错误格在排序后短暂闪红** → 重算发生在重渲染的同一帧内，避免先渲染后校验；由于校验本就逐字重算，视觉上是稳定的。
- **一次应用混合了排序与改名，摘要可能被误读** → 摘要分两句：歌名改动数（多重集差异）+ 已排序分类数；两者都为 0 时保持现有的「无改动」路径。
- **头部空间不足** → 按钮与 keyhint 竞争宽度。允许把 keyhint 收进 `?` 提示（设计规范已有该模式），具体排布在实现时按设计规范处理，不影响本设计的行为约定。

## Migration Plan

无数据迁移：项目文件结构与分类块参数不变，旧项目打开后保存顺序保持原样，直到用户主动排序。回滚即删除按钮与其入口，已排序的数据仍是合法的保存顺序。

## Open Questions

- 头部按钮的具体位置、是否把 keyhint 折叠为 `?`：属于视觉排布，实现阶段按设计规范定稿。
- 「已排序」提示用状态行还是轻提示：两者都已存在，按其他编辑动作的惯例选用即可。
