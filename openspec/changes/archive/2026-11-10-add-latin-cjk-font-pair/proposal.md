# Proposal

## Why

当前分类名、歌名和自由文字各自只有一个 `fontFamily`，默认字体栈又把中文字体排在前面，因此英文也会使用中文字体的拉丁字形。用户无法为同一段文字分别指定“西文字体”和“中文字体”，而中文字体自带的拉丁字形往往不符合预期。

本变更在零构建、零网络依赖的前提下，让英文优先使用西文字体、中文回退到中文字体，并把这一能力做成可独立选择、可持久化的两个字体槽位。

## What Changes

- 在分类名、歌名、自由文字三处字体设置中增加“西文字体”和“中文字体”两个可独立选择的槽位；继续保留手动编辑完整字体栈的入口。
- 样式新增可选 `fontPair: { latin, cjk }` 元数据；`fontFamily` 继续作为实际渲染字符串和旧版兼容字段。存在 `fontPair` 时由它拼出 `fontFamily`，手输完整字体栈时清除 `fontPair`，以手输值为准。
- 字体栈按“西文字体在前、中文字体在后”组合，例如 `"Inter", "Noto Sans SC", sans-serif`，让拉丁字形优先命中西文字体，缺字时再落到中文字体。
- 字体选择器按槽位工作：西文槽位只预览拉丁字符，中文槽位只预览中文字符；“系统默认”按槽位恢复对应的默认字体栈。
- 默认字体拆成默认西文栈和默认中文栈，并组合成西文在前的 `DEFAULT_FONT`。只影响新建样式和“系统默认”恢复，不静默改写已有项目中的字体字符串。
- 明确这是 best-effort：系统不检测字体是否包含某类字形，也不保证中文一定落到中文字体；若西文字体自身包含中文字形，中文仍可能由它渲染。界面不得暗示已经校验过字形覆盖。
- 持久化新增可选的 `fontPair` 字段；没有该字段的旧项目继续按原 `fontFamily` 渲染，旧版本应用忽略新字段。

本次不做：

- 不引入 `@font-face` + `unicode-range` 或逐段绘制来实现确定性分派。
- 不读取 `FontData.blob()`、不解析字体 cmap、不通过像素探测筛选字体。
- 不增加按语言区分的字号、字重或标点策略；不区分中文、日文、韩文分别使用不同字体。
- 不改变 PNG 导出格式、不新增运行时依赖。

## Capabilities

### New Capabilities

- 无。本变更只扩展现有字体选择行为，不引入新的能力边界。

### Modified Capabilities

- `font-selection`: 字体选择入口从单一字体族扩展为西文/中文双槽位；搜索预览、应用选择、默认恢复和持久化要求相应调整，并明确 best-effort 回退边界。

## Impact

- 代码：`js/model.js`（默认字体、`fontPair` 组合）、`js/io.js`（可选字段序列化）、`js/ui.js`（双槽位入口与绑定）、`js/fontpicker.js`（槽位感知的预览和默认项）、`style.css`（字体控件布局微调）。
- 数据：项目 JSON 的样式对象增加可选 `fontPair`；旧项目无需迁移。
- 规格：`openspec/specs/font-selection/spec.md` 需要更新。
- 约束：仍为纯 `html + js`、`file://` 可运行，不新增构建、网络或第三方依赖。
