# Design

## Context

见 `proposal.md` 的动机与 `specs/playlist-editing/spec.md` 的行为契约。实现层面需要知道以下现状：

- 零构建、经典 `<script>`；状态在 `L.app`，界面在 `L.ui`，数据模型在 `L.model`。没有测试套件，验证靠浏览器手动操作。
- 歌单数据是 `project.playlist.categories: [{ name, songs: [] }]`。**分类名同时是身份键**：页面上的分类块用 `element.category` 存分类名，`getCategory`、`getPlacedBlock`、重复导入的 `reconcile/applyImport` 都按名字匹配。
- 没有撤销栈。`changed()` 默认调用 `ui.renderAll()`，后者会重算所有页面的排序、动态行、续表和溢出警告。
- `ui.modal.open` 是单例：每次打开都会清空 `modalRoot.innerHTML`，支持自定义宽度和 `actions`，但没有关闭前钩子；Escape、遮罩、右上角 × 都直接关闭。遮罩监听用了 `{ once: true }`，第一次点击弹窗内部后就会失效（现有小问题）。
- 左侧分类面板 300px；`#category-toolbar` 目前是「导入歌单」+「或拖入 .txt」。

## Goals / Non-Goals

**Goals:**

- 一个不离开应用的歌单微调入口，按分类切换，用多列网格把上百首压缩到可接受的高度。
- 编辑过程不触碰项目数据，点「应用」才一次性写回，且保留已排好的版面。
- 校验规则与导入保持一致，避免“编辑器能存、重新导入却报错”的状态。

**Non-Goals:**

- 分类新增/删除、歌曲跨分类移动或排序、搜索、文本镜像模式、画布内直接编辑。
- 实时预览、撤销栈、协同或后端。
- 改变项目数据模型、保存格式、导出行为，或引入新依赖。

## Decisions

### D1. 弹窗 + 左侧分类栏 + 右侧多列网格

采用 `ui.modal.open` 的宽弹窗：宽度约 `min(960px, 92vw)`，高度约 `min(720px, 84vh)`；左侧分类栏约 180px，右侧网格 `repeat(auto-fill, minmax(160px, 1fr))`，典型窗口下 4–6 列。分类栏和网格各自滚动，标题与底部按钮固定。

理由：一次只面对一个分类的几十首，再叠加多列，比整份歌单的单列列表少一个数量级的滚动。固定列网格在改名时不会像胶囊墙那样整片重排，单元格也更容易做键盘连续编辑。

备选：

- 纯文本镜像：批量修改最快，但仍是“一行一首”的垂直滚动，单条微调没有点击目标。
- 胶囊墙：密度最高，但长度不齐导致换行位置随输入变化，编辑时视觉跳动明显。
- 侧栏就地展开：300px 放不下有意义的网格；拉宽侧栏又挤压画布。
- 画布双击直改：画布顺序是按视觉字宽重排的，不是原始顺序，上百首里找目标反而慢。

### D2. 工作副本 + 应用/取消

打开时从 `project.playlist.categories` 深拷贝出：

```text
working = {
  categories: [
    { originalName: "华语流行", name: "华语流行", songs: ["晴天", ...] },
    ...
  ],
  activeIndex: 0
}
```

`originalName` 只存在于工作副本，用来识别“改名”而不是“删旧建新”。所有输入只改 `working`；点「应用」才写回项目，点「取消」或确认放弃则直接丢弃。

理由：项目没有撤销栈，工作副本是唯一的“反悔”通道；同时避免每敲一个字就触发整页重排。代价是应用前看不到画布效果，这对“微调”场景可以接受。

备选：即时写回 + 额外撤销栈。实现更重，而且会引入“编辑器内撤销”和“项目级撤销”两套语义。

### D3. 表单式校验，而不是提交即拒绝

输入过程中只更新工作副本，不做阻断；在 `input`、`compositionend`、`blur`、Enter 或点「应用」时运行一次整体校验。错误状态：

- 非法输入框标红，保留用户输入，不自动回退。
- 底部显示「N 处待修正」，「应用」禁用。
- 分类名重复时，当前输入框和左侧对应分类都做标记；歌名重复时，冲突的两格都标红。
- 左侧分类行显示工作副本中的名称和歌曲数；名称为空时显示「未命名」并标红，避免出现无法辨认的空白行。

规则与导入一致：`trim` 后分类名非空且分类间唯一；歌名全局唯一、非空、不以 `#` 开头；分类名与歌名允许同名；匹配为精确字符串（区分大小写），不做模糊或大小写折叠。

理由：交换两首歌名时必然出现临时重复；提交即拒绝会让这个操作无法完成。自动回退则会丢掉用户刚输入的内容。

### D4. 分类名是身份：用 `originalName -> name` 映射迁移引用

应用时：

```text
1. 把当前聚焦输入框的值写回 working
2. trim / 归一化，整体校验
3. 构建 renameMap: 只包含 originalName !== name 的项
4. 遍历所有页的 elements：
     type === 'category' 且 renameMap 命中 element.category
       -> element.category = renameMap[element.category]
5. project.playlist.categories = working.categories.map(
     ({ name, songs }) => ({ name, songs: songs.slice() })
   )
6. ui.renderAll()
```

不引入分类 `id`。理由：`id` 会牵动导入、持久化、渲染、导出和现有规范，属于数据模型迁移；本次只需要在应用瞬间建立一次映射，成本低得多。

不采用“删除旧块、按新名新建块”，因为那会丢失位置、尺寸、样式、表格结构和手动列宽。交换两个分类名（A→B、B→A）会被唯一性校验挡住；需要时用临时名中转，规则容易解释。

注意：在编辑器里改名后，若之后重新导入的文件仍用旧名，会按现有导入语义视为“旧分类消失、新分类未放置”。这是 `playlist-import` 的既有行为，本次不改。

### D5. 网格使用常驻 `<input>`，而不是点击后变输入框

每个歌名格直接是一个 `<input>`，设置 `spellcheck="false"`、`autocomplete="off"`、`aria-label`。优点：

- Tab / Shift+Tab 的焦点顺序天然正确。
- 输入框自带浏览器级文本撤销，不需要自己实现。
- 不需要维护“当前哪一格处于编辑态”的额外 DOM 状态。

交互：

- 点击聚焦，不自动全选；双击选词由浏览器处理。
- Enter：提交当前值，焦点按阅读顺序（左到右、上到下）移到下一格；最后一格提交后聚焦添加行。值非法时仍然提交并跳格，否则交换两首歌名时会被卡在临时重复状态。
- Esc：恢复该格获得焦点时的值，并 `stopPropagation()`，避免触发弹窗级 Escape。
- 中文输入法：`compositionstart/end` 期间忽略 Enter/Esc 的提交、跳格和关闭逻辑，避免选词回车被当成提交。
- 删除按钮位于格子右上角，悬停或 `focus-within` 时显示，`tabindex="-1"` 不进入 Tab 顺序；删除后焦点移到下一格或添加行。删除是鼠标动作，键盘流专注连续改名。
- 添加行是网格末尾的虚线输入格：Enter 追加一首并保持焦点；粘贴多行时拦截 `paste`，按 `\r?\n` 拆分，逐行 trim，合法且不重复的行追加，最后用 toast 汇总「已添加 X 首，跳过 Y 行」。

只渲染当前分类，所以典型分类 10–40 个输入框；即使某个分类有几百首，也仍是一次性渲染，暂不做虚拟滚动。校验是 O(n) 的 Map 扫描，几百首无压力。

备选：div 点击后替换为 input。省不了多少 DOM，却要额外处理焦点、Esc 还原和重渲染，不如常驻输入框直接。

### D6. 入口放在分类工具栏，不做双击直入

`#category-toolbar` 增加「编辑歌单」次级按钮，与「导入歌单」并列。项目没有分类时按钮禁用或点击提示先导入。打开时若当前选中的是分类块，默认定位到该分类；否则定位到第一个分类。

不放在顶栏：`editor-shell` 明确规定顶栏只承载项目级动作。也不做侧栏双击直入：单双击混用容易误触，且编辑入口的发现性不如显式按钮；以后需要可以再加。

### D7. 应用后只做一次重绘

应用流程见 D4。写回后直接 `ui.renderAll()`，不逐项调用 `changed()`，因为歌单数据、左侧计数、画布块标题和排版会同时变化。

不需要修正 `state.selection`：本次不删除分类，分类块 id 不变；如果选中的是该分类块，只是标题变了。应用成功后给一条 toast 汇总，例如「已更新：3 处歌名，1 个分类改名」。

### D8. 关闭守卫需要给 `ui.modal.open` 加一个关闭前钩子

现有弹窗的 Escape / 遮罩 / × 都直接 `close()`，无法满足“有未应用修改时先确认”。方案：

- 给 `ui.modal.open` 增加可选 `beforeClose`（或 `canClose`）回调；`close(force)` 在 `force !== true` 时先询问回调，返回 `false` 则中止关闭，`onClose` 不触发。
- 修掉遮罩监听 `{ once: true }` 的问题：改成普通监听，只有 `event.target === root` 时才走关闭，关闭时统一移除，保证第一次点击弹窗内部后遮罩仍然有效。
- 编辑器自己的“放弃修改？”确认用**弹窗内部的内联确认条**，不调用 `ui.modal.confirm`。原因是 `ui.modal.confirm` 会清空 `modalRoot` 并重建，直接销毁编辑器 DOM 和输入状态。

“是否有未应用修改”用工作副本与打开时快照的深比较判断，而不是单纯脏标记；这样用户改了又改回去时，关闭不会多问一次。

### D9. 样式与可访问性

- 弹窗加 `playlist-editor-modal` 类：`body` 改为 `display:flex; overflow:hidden; min-height:0; flex:1`，内部两栏各自滚动；窄窗口下分类栏可缩到 140px，网格最小列宽保持 140–160px。
- 输入框错误态用统一 class（如 `is-invalid`），底部错误计数用 `aria-live="polite"`。
- 删除按钮、分类切换按钮都有 `aria-label`；删除按钮 `tabindex="-1"`，不打断 Tab 连续编辑；当前分类用 `aria-current` 或等价状态。
- 长歌名在格子内截断，`title` 提供全名；不改变行高。

## Risks / Trade-offs

- **改名与重新导入的语义冲突**：编辑器改名后，旧名文件重新导入不会匹配旧块。→ 接受，属于现有导入规则；在设计的 D4 中记录，不改导入。
- **空分类无法在应用内删除**：删光歌曲后分类保留 0 首。→ 接受，这是本次范围；用户可重新导入去掉分类。
- **应用后没有撤销**：工作副本只在应用前有效。→ 应用是显式动作，成功后 toast 汇总；不额外加确认，避免每次应用都多一步。
- **非法值在切换分类后仍然存在**：工作副本保留非法文本，切回时仍标红，应用保持禁用。→ 左侧分类行显示错误标记，避免用户找不到问题。
- **中文输入法误提交**：Enter/Esc 可能在选词阶段触发。→ 用 composition 状态守卫，并在真实中文输入法下手动验证。
- **弹窗单例**：编辑器打开期间不能再打开其他弹窗（会被清空）。→ 编辑器内不嵌套 `ui.modal`；放弃确认用内联条。
- **修改共享 modal API**：`beforeClose` 和遮罩修复会影响所有弹窗。→ 回归测试 `ui.modal.alert`、`ui.modal.confirm`、背景库、导入错误与重新导入确认。
- **超大单分类**：几百首一次性渲染会变重。→ 当前按分类隔离，典型规模无问题；若出现上千首的单分类，再考虑虚拟滚动或搜索。

## Migration Plan

- 无数据迁移，`project.version` 不变；旧项目直接加载。
- 纯增量 UI：移除「编辑歌单」按钮和对应代码即可回滚，项目数据只在用户点「应用」时变化。
- 手动验证路径：打开含多个分类的项目 → 改名（已放置/未放置）→ 增删改歌名 → 多行粘贴 → 制造重复/空名/`#` 开头 → 取消与放弃确认 → 应用 → 看画布排版、左侧计数、保存后重新加载 → 再导入一份同名/改名的文件确认导入语义未被破坏。
